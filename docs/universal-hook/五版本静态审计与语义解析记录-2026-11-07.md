本轮完成了 2.7.1、2.7.2、2.7.3、2.7.4 APKM、2.7.5 五个输入的 GitHub Actions 静态审计。五个版本的 APK/APKM 解包、DEX 盘点、Smali 解析、方法/调用边/类索引生成和组件证据归档任务全部成功；aggregate 成功生成跨版本报告、索引和语义候选匹配。

### 2.1 身份核验的限制

APKTool 成功解码五个版本的 Manifest。当前解码输出中，2.7.1、2.7.2、2.7.3、2.7.5 的 versionCode/versionName 均未能从已解析的 Manifest 根属性中提取。2.7.4 APKM 的 ABI split \`config.arm64_v8a\` 中发现 \`versionCode=294\`，但 base split 没有提供完整版本属性。

因此本轮可靠身份依据是：
1. APK/APKM 输入 SHA-256；
2. Manifest 包名；
3. split 名称及 APKM 组件结构；
4. DEX 数量、DEX SHA-256 和 DEX 头部一致性；
5. 与运行日志或发布渠道信息进行的外部交叉核对。

不能仅凭文件名或 APKTool 当前输出，声称已经确认 2.7.2 APK 与 \`dsprobe.log\` 中的 \`code289-cn\` 是同一个精确构建。后续需增加 Android SDK \`aapt dump badging\` / 等价二进制 Manifest 读取器，并与签名证书摘要一起核验。

### 3.1 DEX 完整性检查

每个 DEX 记录：
- DEX magic/version；
- 实际字节数和 header 声明的 file_size；
- string/type/proto/field/method/class_def 数量；
- DEX SHA-256；
- header Adler32；
- file_size 是否匹配。

本轮生成的五版本索引中，DEX header file_size 与提取文件长度相符。该项是容器/索引完整性检查，不等价于验证所有指令语义正确，也不替代 DEX verifier。

### 3.2 反编译工具状态

APKTool 在五个输入任务中成功产出 Smali。JADX 在部分输入/组件上的退出码为 2 或 3，仍产出部分 Java 文件；这些结果被记录为 best-effort，不把 JADX 退出码非零描述为完整反编译成功。后续语义确认必须回到 Smali/DEX 证据；JADX 输出用于辅助阅读，不作为唯一事实来源。

- caller/callee 邻接索引；

### 4.2 首轮 Resolver 结论及其纠偏

首轮真实索引解析结果：
- 2.7.1：18 个角色全部拒绝；
- 2.7.2：18 个角色全部拒绝；
- 2.7.3：初步接受 1 个角色、拒绝 17 个；接受项是 \`local_api.request\`，候选落在第三方验证 SDK 的 \`cn/fly/verify\` 类，不是 DeepSeek Local API Gateway，属于角色边界错误；
- 2.7.4：18 个角色全部拒绝；
- 2.7.5：初步接受 1 个角色、拒绝 17 个；\`conversation.session\` 候选为 \`Lnw3;->e(Lyu1;Ljava/lang/Long;)Lb70;\`，分数 5.693、次优 5.338，差值约 0.355，仅略高于旧默认门槛 0.35。

这些“接受”仅指静态 Resolver 在首轮配置下给出了一个候选，不表示已验证其语义，更不表示 Hook 已安装。2.7.3 的 Local API 结果已判定为错误角色映射；2.7.5 的 conversation 候选也因 margin 太贴近阈值而需要更严格复核。

### 4.3 本轮已经实施的纠偏

1. 从宿主 APK 静态角色映射中移除 \`local_api_gateway → local_api.request\`。Local API Gateway 是模块侧功能，不应通过 DeepSeek APK 内第三方 HTTP/验证 SDK 的方法来推断存在。
2. \`RolePolicy.minimumWinnerMargin\` 默认值由 0.35 提高到 0.5，避免 0.355 这种近似并列候选被静态自动接受。
3. \`HookCoordinator\` 增加独立安装门槛：
   - HostFingerprint 必须具备包名、versionCode、versionName、签名摘要、DEX 指纹和 ClassLoader 身份；
   - 候选必须同时带有 \`HOST_IDENTITY\` 与 \`RUNTIME_BEHAVIOR\` 两类运行时证据；
   - 只有静态分析证据的候选即使 Resolver 排名第一，也不能进入 HookBackend。
4. 新增测试：模块侧 Local API 不得从宿主 APK 映射；静态候选不得安装 Hook；缺少运行时签名身份不得安装；近似并列候选 fail-closed。

以上修复已提交到当前工作分支，需以其后触发的 Semantic Core CI 结果为最终验证依据。

## 5. 图分析能力与当前边界

### 5.1 已实现

- 调用图：从真实扫描边建立 caller/callee 索引，并统计方法邻域。
- 字段关联：按字段描述符建立 reader/writer 集合，识别跨方法共享字段读写。
- 类型图：读取 class descriptor、superclass 和 interfaces，建立子类与接口实现者索引。
- 控制流摘要：统计条件分支、标签、return 和 throw。
- Anchor rarity：按某锚点在整个宿主方法索引中的出现频率降低通用锚点权重。

### 5.2 尚未实现，不能夸大

- 还不是完整 CFG：尚未建立每个基本块的精确起止偏移、异常边、switch 边和完整后继/前驱图。
- 还不是完整污点分析：字段读写只是跨方法静态关联，没有做寄存器 SSA、对象别名、参数到返回值传播、字符串拼接传播或路径敏感分析。
- 类型图尚未处理完整泛型签名、注解、反射目标、动态代理、ClassLoader 运行时生成类型和 Native 类型边界。
- 协程分析尚未恢复完整状态机字段与 label 状态之间的映射，也未自动识别所有 suspend/resume 生命周期。
- 序列化分析尚未恢复所有 Serializer 注册顺序、多态 discriminator、descriptor 树及 encode/decode 调用链。
- Native 分析目前有 so 文件清单和哈希；JNI 导出/导入、符号恢复、调用点与 Java 层语义的自动关联仍需继续建设。

### 6.3 已知协议行为

- 请求端点：\`/api/v0/chat/completion\`、\`/regenerate\`、\`/continue\`、\`/edit_message\`、\`/resume_stream\`、\`/create_pow_challenge\`、\`/stop_stream\`；历史读取 \`/api/v0/chat/history_messages\`。
- Response handler 会读取 \`x-ds-sse-heartbeat-timeout-secs\`，默认值 10 秒，并将响应体交给 Flow/SSE 解析路径。
- 非 2xx 响应走结构化错误分支，不应被当作正常 Delta 流。
- Parser 以 \`event:\` 和 \`data:\` 为主要输入行；目前没有证据证明完整支持标准 SSE 的 id/retry/多行 data/comment 语义。
- 事件分发包含默认 DeltaCommand、ready、finish、toast、hint、title、update_session、update_file、update_parent_message、close、check_client_update、auto_tts_capability 等分支。
- 2.7.3 与 2.7.5 混淆类名不同；相同混淆名在不同版本可能代表不同功能，不允许按单个类名做跨版本硬映射。

### 6.4 PoW / Native 边界

既有分析发现 2.7.3 与 2.7.5 的 \`librscrypto.so\` 文件哈希一致（SHA-256：\`4571b9bcf08d5f070a47a495bdcd4c77f4a088feee560ed11701ca93c7b56053\`）。JNI 导出函数和内部 helper 已作为只读分析线索记录。算法输入拼接、计数器编码、比较条件和服务端校验语义仍未完全证明。本工程只做结构识别和安全观测，不绕过 PoW、认证或服务端策略。

## 8. 隐私与安全约束

- 不持久化 prompt 原文、消息正文、附件字节、音频转写、Authorization、Cookie、API Key、PoW challenge/salt/nonce 原始值。
- 只允许记录来源标签、模板 ID/哈希、长度区间、模型/工具类型、路由 ID、事件类型、状态、耗时区间、HTTP 状态类别和异常类型。
- 静态扫描输出中对敏感字符串采用脱敏标记；脱敏标记本身不得再触发 prompt 语义锚点。
- 不伪造账号、订阅、额度或服务端能力；不绕过认证、PoW、权限门和服务端策略。
- Hook 失败时保持宿主原行为；未知版本、身份不完整、候选歧义时按角色 fail-closed。
- Agent 工具只有在找到本地执行调用、权限判定和结果回注的闭环后才能标记为本地可执行工具。

## 13. CFG 实际构建、边截断 fail-closed 与五版本复验

### 13.1 CFG 数据结构

本轮在 `scripts/audit_deepseek_apk.py` 增加 `build_smali_cfg`，按方法内可执行指令索引构建保守 CFG：

- 排除 `.packed-switch`、`.sparse-switch`、`.array-data` payload 伪指令，不将其误计为可执行指令。
- 识别条件跳转、goto、switch case/default、顺序 fallthrough，以及 `.catch`/`.catchall` 的异常处理边。
- 通过分支目标、分支后指令、case 标签、异常处理器和 try 区间边界建立基本块。
- 输出 `instruction_count`、`block_count`、`edge_count`、`unresolved_target_count`、`unresolved_targets`、`complete`、`edges`、`edges_truncated`。
- 边列表最多保留 256 条；如果超过上限，必须同时标记 `edges_truncated=true` 与 `complete=false`。未解析标签/异常范围同样使 CFG 不完整。

### 13.2 语义层接入

`StaticProgramGraph` 新增 CFG 结构字段读取。旧的 branch_count/label_count 仅用于诊断，不再单独构造 `CONTROL_FLOW` 证据。只有 CFG 完整且基本块数大于零时才允许生成该证据；边列表截断、跳转目标未解析、旧索引缺少 CFG 时均不提升控制流证据。
